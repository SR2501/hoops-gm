# Model productivity analysis — Claude Opus 5 → GPT-5.6 Sol Fast

Analysis session, off critical path. No production code, backlog, handoff, or governance files were touched.

**Headline: the period boundary and the model boundary are confounded, and the confound is severe. The raw per-model numbers below are real, but they are NOT a like-for-like measure of the two models, because the work changed character at the same time the model did. I could find no clean comparable-work slice spanning the boundary. The honest answer is: these periods are not comparable as a controlled model experiment, and section 4 states exactly why.**

---

## 1. When the switch happened (derived, not assumed)

Mechanism: `session_store_sql` source=`local`, table `assistant_usage_events`, dominant model per day by total tokens.

| day | top model | turns | % of day's tokens |
|---|---|---|---|
| 2026-08-24..27 | claude-opus-5 | 1168–5972 | 96–99% |
| **2026-08-28** | claude-opus-5 | 4133 | **88.7%** (sol-fast debuts: 899 turns, 11%) |
| **2026-08-29** | **gpt-5.6-sol-fast** | 3199 | **91.1%** |
| 2026-08-31..09-05 | gpt-5.6-sol-fast | 802–2957 | 61–99.7% |

`gpt-5.6-sol-fast` has **zero rows before 2026-08-28**. The switch is a step change, not a ramp: opus-5 is 88.7%+ of tokens every day through 08-28, then ≤ a few percent every day from 08-29. **The boundary is the 08-28/08-29 midnight line.** I define Period A = 08-19..08-28 (opus-5), Period B = 08-29..09-05 (sol-fast).

Caveat: local timestamps mix formats; I compared only the 10-char date prefix on both sides, so the boundary is correct to the day, not the hour.

## 2. Raw per-model comparison (the two dominant models, their own periods)

Mechanism: `assistant_usage_events`, main model of each period only (opus-5 in A, sol-fast in B).

| metric | A: opus-5 | B: sol-fast | ratio B/A |
|---|---|---|---|
| sessions | 119 | 56 | 0.47 |
| turns | 44,980 | 12,890 | 0.29 |
| turns / session | 378 | 230 | 0.61 |
| avg turn duration (ms) | 12,391 | 6,249 | **0.50** |
| input tokens / turn | 250,037 | 147,283 | 0.59 |
| output tokens / turn | 851 | 537 | 0.63 |
| nano_aiu (cost proxy) / turn | 22.7B | 12.8B | **0.56** |

**Read literally:** sol-fast turns are ~2× faster and ~1.8× cheaper per turn, with ~40% smaller input context and shorter outputs. Per *turn*, sol-fast is markedly cheaper and faster. This is the strongest, cleanest finding and it is a genuine model/throughput difference — but "per turn" is not "per unit of value," and the turn counts themselves reflect different work (see §4).

Whole-period token totals (all models, 08-08..09-05): Period A opus-5 alone burned 15.7B input tok / 1,347T nano_aiu; Period B sol-fast 1.9B input / 165T nano_aiu. Period A was simply a much larger volume of machine work — again, mostly because of what the work was.

## 4. The confounder analysis (the actual deliverable)

**What the work WAS, per period** — mechanism: classify every file-touch in `git log --name-only` by path.

| area | Period A file-touches | Period B file-touches |
|---|---|---|
| backend | **491** | 141 |
| frontend | 292 | 125 |
| docs | 386 | 168 |
| data/ingest | 71 | 30 |
| quant/model | 33 | 18 |
| bridge | 18 | **49** |
| tests | net **+373 defs** | net +34 defs |

Period A is backend/ingestion/model-plumbing dominated (491 backend touches, 373 new test definitions — the kind of greenfield module work that generates many tests). Period B is surface hardening: backend collapses to 141, bridge (userscript) nearly triples (18→49), and the flagship item is a single React form.

**The draft-setup form is Period B in miniature, and it is why raw counts mislead.** Verified from handoff.md: the browser draft setup flow (PR #164, +2386/−58 across 13 files, 8 commits) was taken through a mutation matrix that grew **42 → 43 → 45 → 46 mutations caught, 0 survived, 0 harness failures at every step**, and a test count of **472 → 475**. That is five internal review rounds producing 3 net tests and 4 added mutation guards.

**Is that churn or quality? The evidence points to quality, not churn:**
- 0 mutations survived across a 46-mutation matrix — each review round *added attributable guards* ("The new guard has an attributable mutation"), it did not thrash.
- commits/PR actually *fell* A→B (6.3 → 4.7, median 3), the opposite of what runaway rework looks like.
- test *deletions* rose in B (63 vs 12) but against far fewer additions — consistent with refactoring an existing surface, not churning new code.

So the five rounds on one form are best read as deliberate hardening of a high-blast-radius UI surface, not the model spinning. But note the honest limit: **token counts alone cannot prove this; the mutation-survival record is what discriminates, and that record is a property of the test suite and the review protocol, not provably of the model.**

**Can any like-for-like comparison span the boundary?** I looked for a work-type present in meaningful volume on both sides:
- backend: 491 vs 141 touches — present both sides but 3.5× heavier in A; not matched volume.
- quant/model: 33 vs 18 — too thin either side to compare per-model productivity.
- bridge: 18 vs 49 — heavier in B; reverse imbalance.
- No single PR or module was independently built by both models on comparable scope.

**Conclusion of §4: there is no clean comparable slice. Every aggregate in §2–§3 is confounded by work type. The per-turn speed/cost advantage in §2 is the only finding robust to the confound, because it is measured within-turn regardless of what the turn was doing — and even that is contaminated if opus-5 was systematically assigned larger-context backend turns (its input/turn is 250K vs 147K, consistent with exactly that).**

## 5. Recommendation (at the confidence it earns)

**Supported by evidence (high confidence):**
- Sol-fast is ~2× faster per turn and ~1.8× cheaper per turn on this workload. For interactive surface/frontend/bridge work of the kind done in Period B, that throughput/cost advantage is real and worth keeping as the default there.
- Output quality did not visibly regress across the switch: mutation matrix stayed at 0-survived, the mandatory "could not verify" discipline held, tests still landed. Nothing in the data shows sol-fast producing worse artifacts.

**NOT supported by evidence (do not claim):**
- Any statement of the form "sol-fast is X% more/less productive than opus-5." The productivity aggregates measure the calendar (backend→frontend shift), not the model. The 260→124 commit and +373→+34 test drops are almost entirely explained by A being module-building and B being surface-hardening.
- That opus-5 is "better for hard model work." Plausible from the input-context asymmetry, but Period B did almost no quant/model work, so the data is silent on it.

**Practical recommendation:** Keep sol-fast as default for frontend, bridge, and CI/surface work — the per-turn speed/cost win is clean and the quality signals held. Before the next statistical-core push (availability model, valuation, backtests — the work that dominated Period A and is where "confident, plausible, wrong" is the documented hazard), run a **deliberate paired trial**: give both models the same bounded quant task and compare mutation survival, calibration-gate outcomes, and reviewer rework. Do not infer that choice from this dataset.

**What to record going forward so this is answerable next time:**
1. Tag each session/turn with a work-type label (backend/quant/frontend/bridge) at capture time — then productivity can be sliced within work-type and the confound dissolves.
2. Log gate outcomes (Model/Adapter/Automation pass-fail, mutations survived, calibration numbers) against session_id and model, so *value* has a measured proxy instead of only tokens.
3. Record review-round count per PR as a first-class field, not something reconstructed from handoff prose.

## What I could NOT verify
- **Hourly boundary:** local timestamp format mixing means the switch is pinned to the day (08-28/08-29), not the hour. A handful of turns could sit on the wrong side.
- **Value:** I have no measure of value, only proxies (mutations survived, tests, merges). "Five rounds = quality" is an inference from the 0-survived record and falling commits/PR, not a proof. A different reviewer could read the same five rounds as over-polishing one form.
- **Model attribution of quality:** the mutation/test discipline is a property of the suite and protocol; I cannot separate "sol-fast wrote good code" from "the gates caught everything regardless of model."
- **Turn semantics across models:** a "turn" for opus-5 (250K input tok avg) and sol-fast (147K) may not be the same unit of work; the per-turn cost ratio may partly reflect context size assigned, not model efficiency.
- **gh reviews:** GitHub review objects are 0 on these PRs; the "review rounds" are the app-internal agent review recorded in handoff.md, which I read as prose, not structured data.
- **PR-number gap (#62→#137):** many PR numbers between the periods never merged to origin/main in this window; I did not audit where they went, so Period A/B PR *counts* are merges-to-main, not total PR activity.

| R44 | **The historical injury-report backfill cannot reach an off-cadence report** | 🟡 | The report has no published schedule. `hoops_gm.ingest.injury_report.backfill` guesses candidate instants per date: `evening_before` (17:30 ET the day prior) in both URL eras, plus either the legacy era's fixed `game_day@13:00 ET` guess (pre-2025-12-22, where the URL truncates to the hour and the parser's 45-minute masthead tolerance genuinely helps recover a nearby guess) or a bounded, tip-off-anchored, **15-minute-grid-aligned** `NEAR_TIP_OFFSETS` set (post-2025-12-22, where the URL is an exact-minute match with **no** drift tolerance at the URL level — a corrected claim; an earlier version of this document wrongly extended the legacy era's 45-minute *recovery* claim to the exact-minute era). Independent review also found a non-grid-aligned tip-off (e.g. 19:10 or 19:40 ET) moved every offset off the source's own quarter-hour marks; `_floor_to_quarter_hour_et` now floors each candidate to the prior 15-minute mark before requesting it, closing that specific gap without widening the request budget. An emergency update published outside all of these instants (e.g. an overnight injury discovered at 3am ET, or a post-2025-12-22 masthead published at a minute none of the bounded, grid-aligned offsets land on) is not reachable by this scheme and is not claimed to be — a disclosed, falsifiable coverage gap in the historical cohort `injury-status-conversion` trains from, recorded per-game via the tool's own `observations` command, the `exclusion_cascade` denominator breakdown, and the `CoverageReport` artifact (now persisted even on an aborted run, and keyed on the exact requested instant so a corrected tip-off cannot silently reuse a stale candidate's coverage), not a correctness bug in what was fetched. A run additionally fails closed via `enforce_expected_game_coverage` before any HTTP call if the requested range's official schedule (`LeagueGameFinder`) has games this project never ingested, so this coverage gap is never conflated with an under-scoped run. **Round-5 review found the measurement itself, not just the source gap, was untrustworthy**: a tautological cascade stage, a conflated `no_candidate_coverage` outcome, inconsistent legacy-row exclusion, scope-unbound persisted evidence, and an anchor-offset mislabelled as realized lead time were all fixed and regression-tested — see `docs/adapters/nba-injury-report.md`. Evidence rows written before migrations `0013`/`0014` (the natural-key fix) carry `import_schema_version="legacy"` and are excluded from every trust-dependent cascade stage; a legacy-only local database must be re-captured (checkpoint reset) before its evidence is trustworthy, it cannot be repaired in place. **A further review round found three more evidence-identity defects in `coverage_for_games` itself**, orthogonal to the source's own coverage gap this row describes: classification trusted a caller-supplied `tipoff_utc` snapshot instead of the database's current value (a schedule correction after discovery could let post-tip evidence pass as pre-tip); an unresolved/unattributable report row vetoed `submitted_zero_listed` for every game on its date rather than only the specific same-date games whose current tip-off is strictly after that row's report timestamp; and persisted coverage matched fetched evidence to games by the surrogate, reusable `NbaGame.id` primary key rather than the NBA's own stable game identifier, so a rebuilt database could let stale coverage transfer to whatever unrelated game later reused that id. All three are now fixed, regression-tested (including a staggered multi-game matrix and a reused-surrogate-id transfer attempt), and old coverage records lacking the new stable-id field are treated as legacy and excluded, not trusted. **A ninth-round review found the fix for the caller-snapshot defect above was itself incomplete** — a fresh re-query is not automatically a fresh read once the same session already has the row in its ORM identity map, an omission `populate_existing=True` now closes — plus two more gaps: persisted coverage's stable-id match lacked full schedule-scope binding (exact game-date and season/season_type, and exact rather than `>=` schema-version matching), and a retracted-tip-off game could be double-emitted while a resolved-but-out-of-scope row could still fan its veto onto unrelated same-date games. All four are fixed and regression-tested, including a genuine two-session/two-transaction race reproduction. **A tenth-round review found classification still mixed database state across two separate statements** (the initial `NbaGame` query and a second one, inside `select_canonical_pregame_observations`, solely for tip-off lookup, that a schedule correction could land between), **that persisted coverage validated per-game schedule scope but never the file's own declared season/season_type or each candidate's own recorded scope** (letting a wrong-scope candidate be silently merged and rewritten under the caller's trusted label), **and that checkpoint settlement identity ignored applicable-game scope entirely** (a genuine `--allow-missing-tipoff` partial day where a later-ingested same-day game's tip-off is *later* than the date's already-known earliest leaves the near-tip candidate's resolved instant, and therefore its checkpoint key, completely unchanged, so the stale narrower settlement was trusted forever). All three are fixed: classification now reads every relevant field in exactly one `SELECT`, proven immune to a real mid-call commit via a `before_cursor_execute` engine hook; the coverage schema version is bumped to 3, candidates self-describe their own scope, and a whole-file or per-candidate scope mismatch is rejected/excluded rather than laundered; and checkpoint settlement now carries the settled applicable stable NBA game ids, reprocessing on scope expansion even when the resolved-timestamp key is unchanged — see `docs/adapters/nba-injury-report.md` and `docs/handoff.md`'s most recent entry. **An eleventh-round review found five more evidence-durability and persistence-boundary gaps**: the single-snapshot query itself still excluded every game the caller had classified `missing_tipoff`, so a tip-off ingested for it mid-call could never be observed within that same invocation; `_persist_coverage` validated per-game and per-file scope but never each candidate's own `evidence_schema_version`, so a legacy or unrecognized-future-schema candidate could still be read back, merged, and rewritten into a freshly "current" file forever; the coverage merge key omitted the canonical masthead timestamp and applicable game-id scope, letting two genuinely distinct fetched records (a corrected masthead, or a changed game scope) collapse under one key rather than coexisting; the importer's own internal flush sat outside `run_backfill`'s commit-failure recovery boundary entirely, so a flush-time failure aborted the whole run rather than being recorded as one candidate's unsettled error; and this document's own backlog entry overclaimed a representative, conversion-ready cohort relative to the small non-representative sample actually on record. All five are fixed and regression-tested, including a genuine promoted-missing-tipoff concurrency race, real serialized future/legacy-schema quarantine at the load+merge+save boundary, coexistence/dedupe proofs for the expanded merge key, and a genuine NOT-NULL constraint violation at flush time (not a mocked commit) — see `docs/handoff.md`'s most recent entry. **A round-11 follow-up review found the future-schema-version quarantine itself still crashed the loader on a realistic future record**: `CoverageReport.from_json` always unpacked a raw candidate's entire dict as keyword arguments to `CandidateCoverage` before ever inspecting `evidence_schema_version`, so a future version that added a field (the realistic shape a real future version would take, not merely a bumped integer) raised `TypeError: unexpected keyword argument` and crashed the whole load — taking down both the `observations` CLI path and `_persist_coverage`'s own internal read of `existing` candidates; a renamed or dropped currently-required field (e.g. `report_date`) crashed with a *different* `TypeError` (missing required argument) for the same reason. Fixed by inspecting `evidence_schema_version` first and routing anything not exactly current to a `_quarantined_incompatible_schema_candidate` placeholder that never interprets the record's other fields at all, plus filtering a current-version record's own keys to the dataclass's known field names before construction so a stray key can never reach it either — regression-tested with genuine added-field and renamed-required-field raw JSON through both the `CoverageReport.from_json`/`coverage_for_games` observations path and the real `_persist_coverage` load+merge+save path. The same review also found the backlog's dependency graph let `injury-status-conversion` appear structurally ready once its three listed dependencies were all marked done, even though the representative cohort its own prose says does not yet exist was never itself a tracked dependency; `docs/backlog.md` now tracks that cohort as its own explicit item, `injury-conversion-cohort-population`, and `injury-status-conversion` depends on it | `data-engineer` |

## Realised

| Date | ID | What happened |
|---|---|---|
| 2026-08-17 | R25 | PR #1 claimed enum columns render as VARCHAR + CHECK and that `DateTime(timezone=True)` is portable. Independent review found neither held: `Enum.create_constraint` defaults to `False` in SQLAlchemy 1.4+, so 17 enum columns had 0 CHECK constraints; and SQLite silently drops the offset, so `tipoff_utc` stored local wall-clock time — four hours wrong, and correct on Postgres from the identical write. Both were caught only because a reviewer executed the claims rather than reading them. Root cause: no CI job runs against Postgres, so every portability assertion was static analysis of metadata. **Lesson: a portability guarantee that is never exercised across the seam is a belief, not a guarantee.** **Closed 2026-08-17:** both bugs fixed and the systemic hole closed rather than patched — the whole suite now crosses the seam every push. Findings 1, 2 and 6 of that review were all invisible to the five static portability tests and would have been caught immediately by the new job. The standard this sets, carried into the Adapter and Model gates and into every subsequent phase brief: **a guarantee is only as good as the test that goes around the abstraction and proves it.** |
| 2026-08-17 | R29 | The account-wide private-repository Actions quota was exhausted, stopping every gate before its first step. The owner made the repository public, restoring CI without a spending change; PR #3 then merged the scheduled live-smoke repair. |

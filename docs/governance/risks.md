| R30 | **`BoxScoreSummaryV2.InactivePlayers` silently returns zero rows after 2025-10-21** | 🔴 | Found 2026-08-17 by bisection during Phase 2. V2 returns inactives for 2025-10-21 and **zero rows for every later date across the whole 2025-26 season**; `BoxScoreSummaryV3` carries them correctly under `homeTeam.inactives` / `awayTeam.inactives`. V2 is the endpoint most public examples use, so the obvious implementation would have produced an availability ledger with **no inactives for the entire most recent season, with no error and no failing test**. Direct hit on the project's central pillar. Mitigation: use V3; contract test must assert a **non-zero inactive count for a known mid-season date**, not merely a 200 response | `data-engineer` |
| R31 | Fantrax `getLeagueInfo` returns HTTP 200 with an error envelope | 🟡 | A client trusting `response.ok` parses the error as data. Verified 2026-08-17 with a missing `leagueId`. Handled as a distinct non-retryable error class; contract test pins the envelope shape | `data-engineer` |
| R32 | Fantrax `team` is `(N/A)` for 1,206 of 1,788 player rows | ✅ **Addressed** | Two thirds of the payload cannot contribute team evidence to identity matching. **Absent evidence and disagreeing evidence are not the same**, and a single `confidence` float cannot express the difference — which is what a human needs when adjudicating the tail via `is_manual_override`. **Resolved in Phase 2:** per-field match evidence implemented as four three-valued columns defaulting to `unknown` at the database level, so the pessimistic default survives a raw insert. Phase 1's open question is closed on evidence | `data-engineer` |
| R33 | **A widened enum is invisible to Alembic autogenerate** — `create_all` and the migration chain can diverge | 🔴 | Found in Phase 2 by executing it. Adding `fantrax_sportradar` to `ExternalSource` was accepted by a schema built with `create_all` (which the test suite uses) and **rejected by a migrated database**, with `alembic check` reporting no drift. Green tests, broken production, no warning. Fifth instance of the believed-and-false pattern. Mitigation: a test asserting every enum member is accepted by a *migrated* database, not just a created one. **Generalise the concern** — any divergence between `create_all` and the migration chain is invisible to the suite that only uses the former | `backend` |
| R34 | `batch_alter_table(copy_from=...)` takes different code paths on SQLite and Postgres, and only SQLite has run | 🔴 | The Phase 2 migration rebuilds tables via batch mode. On SQLite this is a copy-and-rename; on Postgres it takes a different path entirely. **Only the SQLite path has ever executed**, because the Postgres CI job has been unavailable since R29. Risk of dropped constraints, lost defaults, altered column ordering or data loss on the first real Postgres run. Do not migrate a Postgres database until CI is restored and this job has run | `backend` |
| R35 | **A full absence produces no row in any endpoint** | 🟡 | A player out injured for a month is not "inactive" in any box score — he simply does not appear. Absence is therefore only detectable by inferring from roster membership crossed with scheduled games. Flagged in Phase 2 for Phase 4: the participation ledger records what was *observed*, and `quant` must construct the absent rows rather than assume the ledger is complete. A model trained on observed rows alone would systematically underestimate missed games | `quant` |
| R36 | **`gameEt` claims UTC and is Eastern** — a well-formed value that lies about itself | 🔴 | Found in Phase 2 by printing real fixture values rather than reading the parser. The same payload carries `gameTimeUTC: 2024-12-01T20:30:00Z` and `gameEt: 2024-12-01T15:30:00Z` — five hours apart, both marked `Z`. Verified independently from the committed fixtures. `game_date` was derived from the UTC tipoff, so game `0022500560` (`gameTimeUTC 2026-01-13T00:30Z`) was dated the 13th when `LeagueGameFinder` and local reality both say the 12th — **wrong for every game tipping after 7pm Eastern, which is most of them**. `player_participation` joins on `game_date`, so a day's participation would have shifted onto the wrong date and the availability model would have absorbed it as real signal. Fixed: `game_date` now comes from `gameEt`'s date, pinned by three contract tests. **This is a distinct class from R25/R33** — `UTCDateTime`'s strictness could not have caught it, because the value is not naive but mislabelled, and would have survived a correct fix for every previous instance | `data-engineer` |
| R12 | Auction inflation model wrong under live conditions, never tested at speed | 🟡 | Validate against the mock corpus before the real draft | `quant` |
| R13 | Overfitting to a small mock corpus when calibrating opponents | 🟢 | 10+ mocks minimum; treat opponent models as priors, not truth | `quant` |
| R23 | **Fantrax exposes no NBA.com player id**, so there is no clean anchor pair for the crosswalk | 🔴 | Verified live 2026-08-17: `getPlayerIds` returns `statsIncId`, `rotowireId`, `sportRadarId` only. The join to `nba_api` is fuzzy from the first step. **`sportRadarId` bridge investigated and ruled out (Phase 2):** no free stable dataset maps a Sportradar GUID to an NBA person id; the open ID datasets carry BBRef/ESPN/Spotrac and are themselves name-matched, so using one would launder a name match into an apparent id match. Sportradar's own mapping endpoint is a commercial subscription (owner-only). Evidence in `docs/adapters/fantrax-official.md`. Mitigation is therefore name+team+position matching with **per-field match evidence** (R32), confidence, recorded match method, and manual override treated as final. All three Fantrax ids are still stored — they de-duplicate *within* Fantrax, where genuine duplicate names exist, and would make a bridge instant if one ever appears | `data-engineer` |
| R24 | `getPlayerIds` mixes non-player rows into the player payload | 🟡 | Team entities appear alongside players (`position: "Tm"`, `#` in the id, e.g. `40220#3020`). Filter explicitly on ingest; a naive importer creates garbage identity rows. Names are `"Last, First"` and need normalising | `data-engineer` |
| R25 | Portability claims are static analysis only — nothing runs against Postgres | ✅ **Closed** | Found by review of PR #1. **Resolved 2026-08-17:** `psycopg` declared, and a CI job now runs `upgrade head`, `alembic check`, `downgrade base` and the entire suite against a real Postgres 16 service on every push — 90 passed, 1 skipped, clean on both dialects. The CI password contains `%` and `#` so the pipeline is itself a permanent regression test for the Alembic interpolation bug | `backend` |
| R28 | Enum CHECK constraints are excluded from Alembic drift detection | 🟢 | Accepted tradeoff. SQLAlchemy reflects enum CHECKs from the database but omits them from metadata (internal `_create_rule`), so including them reports 18 phantom removals forever and leaves `alembic check` permanently red — which is not a weaker signal but no signal, since nobody reads a check that never passes. Compensating control: `test_database_guarantees.py` verifies the constraints on the actual created table on both dialects every run, inserts a bogus value via raw `text()` and requires the database to refuse it, and includes a positive control so the rejection test cannot pass vacuously. Residual risk — a hand-edited enum constraint in a long-lived local database — is not caught. Acceptable for a tool whose schema is rebuilt from migrations | `backend` |
| R26 | **`cdn.nba.com` live feeds return 403 from the dev machine** — the free live scorecard source is unreachable | 🟡 | Verified 2026-08-17: Akamai "Access Denied" (ref `#18.6b07d417`) on `liveData` and `staticData` paths, via curl, PowerShell and `nba_api.live`. **Diagnosis refined:** not TLS fingerprinting — impersonating Chrome 124, Chrome 131 and Safari 17 via `curl_cffi` all still return 403. The machine routes through **Microsoft Entra Global Secure Access**, so traffic egresses from cloud IP ranges rather than the residential connection, and Akamai denies those ranges on the CDN JSON paths while allowing `www.nba.com` from the same address. **Confirm from a device not enrolled in GSA** (a phone on the same wifi is the fastest test). | R37 | **No verified free source of average auction value (AAV)** | 🟡 | Exposed by the auction confirmation. | R38 | **AAV calibration is circular unless the corpus is kept clean** | 🟡 | Mock participants price players from the same public AAV we seed from, so early mock clearing prices partly echo the seeds rather than independently testing them. | R39 | **AAV does not transfer between league configurations** | 🟡 | A $200 budget in a 12-team league with 13 roster spots produces entirely different dollar values than $100 in a 10-team with 10 spots. | R40 | **No official injury report exists on draft morning** | 🟡 | The NBA official injury report is published per-game and the season opens *after* the 18 October draft, so the `injury-report-ingest` built for the regular season covers nothing on the day it matters most. | R41 | **Aggregate contamination — rankings and AAV carry hidden availability** | 🔴 | Published rankings, AAV and consensus tiers already contain production, an availability assumption, a scoring format and often positional scarcity. Third instance of laundering derived information into apparent independent evidence, after R23 and R38. Mitigation is ADR-008: layers are ordered, aggregates are terminal, external rankings may only be compared against, and a test rejects any flow from a higher layer to a lower one | `quant` |

## Realised

| Date | ID | What happened |
|---|---|---|
| 2026-08-17 | R25 | PR #1 claimed enum columns render as VARCHAR + CHECK and that `DateTime(timezone=True)` is portable. Independent review found neither held: `Enum.create_constraint` defaults to `False` in SQLAlchemy 1.4+, so 17 enum columns had 0 CHECK constraints; and SQLite silently drops the offset, so `tipoff_utc` stored local wall-clock time — four hours wrong, and correct on Postgres from the identical write. Both were caught only because a reviewer executed the claims rather than reading them. Root cause: no CI job runs against Postgres, so every portability assertion was static analysis of metadata. **Lesson: a portability guarantee that is never exercised across the seam is a belief, not a guarantee.** **Closed 2026-08-17:** both bugs fixed and the systemic hole closed rather than patched — the whole suite now crosses the seam every push. Findings 1, 2 and 6 of that review were all invisible to the five static portability tests and would have been caught immediately by the new job. The standard this sets, carried into the Adapter and Model gates and into every subsequent phase brief: **a guarantee is only as good as the test that goes around the abstraction and proves it.** |
